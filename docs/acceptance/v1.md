# Woof v1 acceptance criteria

Status: planned verification, not a record of passing tests. Each implementation
claim needs evidence from the target code revision and runtime versions.

## Required end-to-end flow

Start from a Claude Code caller using Woof's native integration without MCP.
Submit a non-trivial input object with task details, acceptance criteria and
context. Woof starts the builder and reviewer through Herdr without manual pane
coordination. Arrange for the first review to request changes, then pass after
repair.

Record the requests, accepted artifacts, envelopes, run events and terminal
result. Verify all of the following:

- The same builder identity and native session perform build and repair. The
  reviewer retains its intended identity across both reviews.
- Both reviews produce substantive artifacts tied to the corresponding changes.
  The builder reads the first accepted artifact directly during repair.
- A valid failed review completes the review stage and triggers repair; it does
  not masquerade as a runtime failure.
- The final gate refers to the repaired change and passing review. Structured
  completion and artifact references reach the caller.
- Herdr status and an external observer agree with the SDK state while work is
  active, without parsing terminal text.

## Verification matrix

| Area               | Scenario                                                                        | Required evidence                                                                        |
| ------------------ | ------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Input              | Nested structured input and invalid input                                       | Valid input reaches the request intact; invalid input fails before worker launch.        |
| Artifact authority | Review contains detailed findings                                               | Downstream reference identifies the exact accepted review, not a paraphrase.             |
| Required output    | Envelope exists but artifact is missing, partial, stale or structurally invalid | No accepted stage completion or gate transition.                                         |
| Consistency        | Envelope verdict disagrees with artifact control metadata                       | Rejection identifies the disagreement.                                                   |
| Format repair      | Worker submits invalid control data, then corrects it                           | Same agent corrects the contract within a separate format-repair budget.                 |
| Exhausted repair   | Repeated invalid submissions                                                    | Explicit limit/reason; no silent success and no infinite prompting.                      |
| Duplicates         | Identical, conflicting, stale and late submissions                              | One acceptance/transition; repeat receipt or explicit rejection as appropriate.          |
| Correlation        | Two runs or attempts submit out of order                                        | No result is accepted for the wrong owner or visit.                                      |
| Runtime state      | Idle/done/unknown arrives without valid result                                  | Stage remains unresolved; bounded policy eventually explains the exit.                   |
| Delivery           | Prompt reports timeout or stalled delivery                                      | No blind duplicate work; uncertainty is visible and reconciled or terminated.            |
| Blocking           | Worker needs permission or an answer                                            | Run identifies the block and owner; resolution continues work, timeout exits explicitly. |
| Failure            | Worker exits or its pane disappears                                             | Failure and retained artifacts are visible; no fabricated completion.                    |
| Limits             | Repeated gate rejection and repeated verification failure                       | Review and non-review loops both reach a finite bound.                                   |
| Cancellation       | Cancel while work is active; result arrives afterward                           | No new stage dispatch and no resurrection by the late result.                            |
| Observation        | Subscribe during a run; disconnect and reconnect                                | No missing transitions; final projection agrees with the current snapshot.               |
| Runtime loss       | Run owner dies                                                                  | Observer reports loss instead of indefinitely claiming active work.                      |
| Configuration      | Project shadows user defaults; invalid role/provider; config changes mid-run    | Provenance is correct, invalid plans fail early, active resolution remains stable.       |
| Reuse              | Add `plan-build-review` and an external small workflow                          | New definitions work without name-specific engine branches.                              |
| Optional adapters  | No MCP server, no community plugins, SDK without Woof UI                        | Core flow and observation remain usable.                                                 |

If caller-independent hosting or crash resume is included, add explicit caller
exit and runtime-restart cases. Verify repository effects occur once under the
promised recovery semantics. Otherwise document those limits without claiming
durability beyond inspectable state and artifacts.

## Evidence by layer

Use unit tests for graph validation, transitions, counters, configuration
resolution, envelope/artifact validation, and state consistency. Use scripted
runtime tests for ordering, stale signals and duplicate delivery. Run binaries,
loaders, packaging and submission channels in real processes so the test runner
cannot hide runtime differences.

Live acceptance must cover the complete caller-to-worker-to-caller flow with
actual Herdr agents. Record the code revision, runtime/provider versions,
configuration, commands, input fixture, event trace, artifact locations, and
observed outcome. Inspect artifact content and the repository result, not only
file existence or event counts.

`bun run verify` is the foundation gate: typecheck, lint, formatting, version
consistency, tests, build, and the packed-package smoke test. It proves the
package and diagnostic surface only. A passing foundation or scaffold check is
not v1 acceptance.
