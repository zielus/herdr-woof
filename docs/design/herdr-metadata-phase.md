# Next phase: use the existing Herdr plugin, then close display gaps

Status: proposal, 2026-09-17. Based on source at `87c9ca3` (Woof 0.1.2).
Start with the [source and saved-configuration audit](../research/herdr-plugin-audit.md).
The plugin is already present and registered in the saved local setup. First
configure and verify its use; extend the publisher only for demonstrated gaps.
This phase does not build a sidebar, workspace preset manager, or another engine.

## Goal

While several worktrees have agents running, the operator can immediately tell
which agents belong together and what their roles are. Expose the current stage
without counters where the available fields permit it; record the gap otherwise.
Herdr remains responsible for lifecycle indicators and workspace activity.

Woof publishes facts it owns. The operator chooses sidebar rows and styling in
Herdr configuration. Existing plugins remain responsible for workspace layouts,
project pickers, activity summaries and automatic display naming.

## What already exists

- [The manifest](../../herdr-plugin.toml) registers `doctor`, `status`, `start`
  and `cancel`. Reuse these actions and their project-context resolution.
- [The metadata publisher](../../src/host/metadata.ts) sends `$woof` to the host
  and agent panes and `$woof-role` to agents. It refreshes every 10 seconds with
  a 30-second live TTL and uses a 10-minute terminal TTL.
- Reports are serialized and coalesced; failures are logged without changing
  the workflow result. Blocking and terminal outcomes already trigger notifications.
- `$woof` combines stage and visit/attempt/round counters. There are no separate
  model, stage or worktree tokens and no workspace metadata publication here yet.

Keep the implemented behavior documented in
[plugin surfaces](../integrations/plugins.md). The new contract below is proposed,
not already available. Retain the old tokens during migration so existing custom
sidebars continue to work; the recommended new sidebar omits the counter string.

## Responsibility boundary

| Concern                                                           | Owner                                                                                                            |
| ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Working/idle/blocked/done/unknown                                 | Herdr's lifecycle authority; never inferred from a Woof output token.                                            |
| Branch, worktree operations and workspace activity                | Herdr/Git. Woof may project verified checkout context into custom fields where the sidebar lacks a native token. |
| Role, configured agent kind/model, workflow, run and stage        | Woof, using resolved plans and accepted run state.                                                               |
| Agent ordering, group headers, row layout, colors and keybindings | Herdr and the operator's configuration.                                                                          |
| Generated activity description and automatic display names        | Optional third-party integrations; not generated by this phase.                                                  |
| Workspace/layout presets                                          | Existing plugins; Woof only consumes the resulting context.                                                      |

2. Apply the optional current-version sidebar configuration through the operator's
   normal setup flow. Keep workspace context on each agent and native branch and
   activity on each Space. Use matching workspace-label colors only if helpful.
3. Observe an intended Woof run with agents in two worktrees. Confirm roles,
   lifecycle indicators, metadata refresh and existing notifications.
4. Record what remains missing. A separate kind/model field and a stage without
   counters are known source gaps. Extra worktree identity is conditional on native

   separate optional extension with multi-run complexity.

The detailed proposal below is a menu of follow-ups, not approval to implement
every field. The first deliverable can be a working personal configuration and
evidence, with no Woof code change. No personal configuration is installed by
this documentation change.

## Candidate metadata contract after the adoption check

Names below are literal token keys, referenced with `$` in sidebar configuration.
Keep values small and publish no prompts, secrets or artifact bodies. Unknown
values are absent, not guessed. The source and token names are a public display
contract; document any future change.

| Token                                     | Target                                   | Meaning                                                                                                        |
| ----------------------------------------- | ---------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `woof-role`                               | Agent pane                               | Assigned responsibility; preserve the existing key.                                                            |
| `woof-kind`                               | Agent pane                               | Configured CLI kind such as `claude` or `codex`, separate from a mutable display name.                         |
| `woof-model`                              | Agent pane                               | Model from resolved launch configuration, not a claim to observe in-session model changes.                     |
| `woof-stage`                              | Agent and host panes                     | Current assigned stage ID with no counters; clear when no stage is active.                                     |
| `woof-workflow`                           | Agent and host panes                     | Workflow definition name.                                                                                      |
| `woof-run`                                | Agent and host panes                     | Run ID, bounded to Herdr's display limit; full identity stays in inspection output.                            |
| `woof-state`                              | Host pane                                | Woof run status/outcome, separate from Herdr's agent state.                                                    |
| `woof-worktree`                           | Agent and host panes; eligible workspace | Short checkout label for the run's repository context, including the main checkout.                            |
| `woof-tree-key`                           | Same as worktree label                   | Stable, short identifier distinguishing that checkout from others with similar labels.                         |
| `woof-branch`                             | Agent and host panes                     | Branch of the run checkout; a truthful detached/unborn label when appropriate. Space rows use native `branch`. |
| `woof-stage`, `woof-workflow`, `woof-run` | Eligible workspace                       | Values only when a single active run provides an unambiguous projection.                                       |
| `woof-activity`                           | Eligible workspace                       | `multiple runs` when several runs are active; otherwise absent. No stage-progress count.                       |

An eligible workspace is a verified runtime workspace associated with the managed
run. Do not treat the plugin checkout or the caller's launch-time environment as
the worker's workspace. Resolve the actual target through supported Herdr data.

## Conditional extension: explicit worktree identity

First try native workspace labels on each agent, with consistent names supplied
by the operator or preset plugin. The following contract applies only if that
setup cannot reliably distinguish the user's worktrees.

Every managed agent from the same checkout receives the same worktree label and
key. The matching workspace row uses those same values. Different worktrees in
the same repository receive different keys. The key is independent of role,
model, run ID, branch renaming and automatic agent naming.

Derive checkout identity from verified Git worktree context and runtime host
identity, not from a branch name or directory basename alone. Use a deterministic
short key that survives publisher restart; define collision handling before
implementation. Preserve the key when shortening labels for narrow sidebars.
Paths are resolved on the target host, not assumed to exist on the client.

The initial promise is visual association in a flat Agent list: repeated readable
labels and keys, optionally styled by the user. The documented Herdr sidebar
configuration does not establish a `group_by = "worktree"` feature. Do not invent
such a setting or promise collapsible groups. True Agent-list grouping belongs
in Herdr or an existing navigation plugin, if supported.

Keep unmanaged agents visible through native `workspace`, `agent` and state
fields. Do not take over every agent to fill missing role/model metadata.

## Rules for any publisher extension

Extend the existing publisher rather than adding a second scheduler. Read stage
and assignment facts from the existing snapshot/host interfaces. Verify stage
coverage for deterministic check stages as well as agent attempts; `verify` must
not disappear merely because no agent owns it.

Retain bounded/coalesced reports and expiring values. Refresh live context,
re-publish after observation recovers, and clear obsolete keys on transitions,
terminal outcomes and ownership changes. A final outcome may remain briefly;
an old active stage must not. Re-resolve pane/workspace context after moves, and
never refresh old role/run data onto a replacement agent. Token patches are not
guarded by Herdr's display-label targeting flags, so the publisher must validate
ownership before reporting. Sequence numbers need a restart-aware policy.

Worktree tokens describe the run checkout. If a pane moves to another workspace,
its run association remains explicit; it must not cause the destination workspace
to advertise a false checkout. For mixed worktree contexts in one workspace,
omit its single worktree key/label and retain accurate labels on each agent.

If workspace-level stage display is selected, its metadata needs one reconciled
view of all active runs in that workspace.
Several independent hosts must not race to set or clear a single stage token.
Choose a bounded publisher ownership/reconciliation mechanism during planning,
without adding workflow coordination to the display layer. With multiple runs,
clear singular run/stage/workflow fields and publish `multiple runs`; restore the
single-run view when appropriate. One run finishing must not erase another's data.

Touch only Woof-owned keys. Preserve metadata from summary/naming plugins and
Herdr's lifecycle authority. Metadata failures may reduce display freshness but
must not change scheduling, artifact acceptance, cancellation or terminal outcomes.

## Required acceptance evidence

For M0, record the actual loaded configuration, registration/action results, and
whether native labels and existing role metadata distinguish the two worktrees.
Do not mark absent new fields as implemented. The scenarios below apply to each
selected extension; deferred extensions remain explicitly unverified.

- Two worktrees of one repository, with a builder and reviewer in each: an operator
  can pair agents with the correct checkout without opening their conversations.
- Same directory/branch labels in different repositories or hosts remain distinct;
  symlink aliases of one verified checkout do not create a second identity.
- Native working/idle/blocked indicators remain visible and unchanged by Woof.
- Current stage includes check work and clears at completion; no `3/5`, visit,
  attempt or round counters appear in the recommended sidebar.
- Two runs in one workspace produce an honest combined display; finishing either
  one does not erase the survivor's metadata. Mixed worktree contexts are explicit.
- Publisher death expires stale data; restart, pane move and agent replacement do
  not attach old metadata to unrelated work. A metadata failure cannot fail a run.
- Configured model is not represented as observed model; unknown values disappear.
- Existing title/summary plugins and unmanaged agents continue to display normally.
- Evidence includes commands, code revision, Herdr version, metadata responses,
  and screenshots or a manual display record. Automated projection tests alone
  do not establish that grouping cues are readable in the real sidebar.
